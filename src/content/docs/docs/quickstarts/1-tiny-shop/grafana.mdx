### One trace across both apps

**Explore → Tempo → TraceQL**:

```txt title="TraceQL"
{ resource.service.name = "tiny-shop-backend" && name = "charge card" }
```

Open the newest trace. Its root is now the browser:

Click any backend span: `session.id` and `user.id` are on it, copied from the browser's `baggage` by the `BaggageSpanProcessor`. That is how you go from a backend span to the session of the person who caused it.

<Aside>The root is still `POST /api/checkout`, without the browser span? `propagateTo` does not match the API URL (use the RegExp), or the page was not reloaded after editing `rum.js`.</Aside>

### Browser events

**Explore → Loki**:

```txt title="LogQL"
{service_name="tiny-shop-frontend"}
```

You see `session.start`, `navigation`, `cart.added`, `http.request.failed` (the 500), `exception` (the thrown error) and `web_vital` records, each with `session_id`. Each is an OpenTelemetry log record with an `event.name`; Loki shows the attribute `session.id` as `session_id`.

### The session

**More apps → ouo11y RUM → Sessions**.

## What you should see

Your session is `crashed` (the uncaught error), with its traces and a replay of what you clicked: the same visit you just found piece by piece in Tempo and Loki, in one place.

A session's status is the worst thing that happened in it: an uncaught exception makes it **crashed**, a failed request or a handled exception **errored**, nothing at all **healthy**. See [Sessions and health](/docs/concepts/sessions/).

You are done. The last page stops the stack and lists what to check when something does not work.
