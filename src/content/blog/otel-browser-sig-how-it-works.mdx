[Part 1](/blog/otel-browser-state-2026-10/) said which packages to use today. This part is about the people and the process behind them: if you want to know what the browser packages will look like in six months, you read what the Browser SIG discussed last Thursday.

A SIG (special interest group) is how OpenTelemetry organises work: a group with a charter, a weekly call, public notes, a Slack channel and one or more repositories. Anyone can join the call.

## From a corner of opentelemetry-js to its own SIG

Browser tracing is as old as OpenTelemetry JS itself. The [repository](https://github.com/open-telemetry/opentelemetry-js) opened in May 2019, and the first browser tracer was on npm five months later. For six years the browser packages lived next to the Node.js ones, reviewed by the same people, following the same specification. A [Client Instrumentation SIG](https://github.com/open-telemetry/community/blob/main/sigs.md#client-instrumentation) worked on shared ideas for browsers and mobile, such as sessions and events, and still meets.

The pressure that split things out shows in two places. The [Browser Phase 1 proposal](https://github.com/open-telemetry/community/blob/main/projects/browser-phase-1.md), merged in June 2025, argues that the browser differs from Node.js enough to need its own work: unloading a page, scarce CPU and network, no gRPC, bundle size, one user per runtime, sessions that span page loads, and no async context. And the JS repository was planning a 3.0 that would merge its tracing SDKs into one package with no browser helpers, which forced the question of where fetch, XHR and the web utilities should live.

The proposal took a narrow first step on purpose: stabilise instrumentation and the data model first, keep using the existing JS SDK, and decide on a browser SDK later. It named Ted Young (Grafana Labs) as project lead and listed implementers from ServiceNow, Honeycomb, Microsoft, Embrace, Elastic and Cisco.

The notes then show the repository decision step by step. On 21 August 2025 a new repository was first raised; on 28 August the goal of the meeting was to decide on one; on 4 September the SIG asked who would maintain it. The repository was [created on 11 September 2025](https://github.com/open-telemetry/opentelemetry-browser). In November 2025 the JS maintainers proposed making browser maintainers code owners for the browser packages still in the JS repositories, and today the [JS `CODEOWNERS`](https://github.com/open-telemetry/opentelemetry-js/blob/main/.github/CODEOWNERS) lists `@open-telemetry/browser-maintainers` for fetch, XHR, `web-common`, the browser detector and `context-zone`.

In May 2026 the notes record a principle that explains many later choices: as long as the APIs match and correct OTLP comes out the other side, the browser may make its own design decisions, and in return the SIG should write down its reasons. The [event catalog](https://github.com/open-telemetry/opentelemetry-browser/blob/main/docs/browser-observability-model.md) and the [roadmap](https://github.com/open-telemetry/opentelemetry-browser/blob/main/docs/roadmap.md) are where those reasons live.

## What was decided this autumn

Notes are short, so we link the issue or PR behind each item and say what has happened since.

**22 October 2026.** The SIG agreed to a proposal to close the open browser convention questions one decision per meeting ([semantic-conventions-client-side#34](https://github.com/open-telemetry/semantic-conventions-client-side/issues/34)), starting with the scope of document load, then INP attribution. Document-load work is to be split into smaller PRs: the span instrumentation, context for resource-timing events, and linking the document-load span to the server's trace through a meta tag. A discussion opened on instrumentation config becoming static, and on when a config change should apply (next session, or next record). Martin Kuba shared a [pull request dashboard](https://github.com/open-telemetry/opentelemetry-browser/issues/517). A release was planned for that week; it [shipped the same day](https://github.com/open-telemetry/opentelemetry-browser/releases).

**15 October 2026.** OTel JS 3.0 was announced for the following Monday (it shipped 20 October). A proposal to move the [OpenTelemetry Demo](https://github.com/open-telemetry/opentelemetry-demo) frontend to the new browser packages was raised with the Demo SIG; the roadmap also asks for this. The browser [migration guide](https://github.com/open-telemetry/opentelemetry-browser/pull/479) was ready for review (merged 22 October), with a request to add a table of key changes. Also on the agenda: a proposal for migrating document load ([#327](https://github.com/open-telemetry/opentelemetry-browser/issues/327)), the [versioning and deprecation policy](https://github.com/open-telemetry/opentelemetry-browser/pull/497) (merged 17 October), resource detectors in the SDK ([#460](https://github.com/open-telemetry/opentelemetry-browser/issues/460)) and moving the browser detector over ([#459](https://github.com/open-telemetry/opentelemetry-browser/pull/459), merged 19 October). On the base instrumentation class, the group asked whether "initialize" and "enable" should be separate, with consent rules such as GDPR in mind, and took an action to open an issue about a global enable and disable for the SDK.

**8 October 2026.** The "with tracing" example still used the classic fetch and XHR instrumentations; the action was to migrate it ([#485](https://github.com/open-telemetry/opentelemetry-browser/pull/485), merged 13 October). Reviews were requested for element timing ([#396](https://github.com/open-telemetry/opentelemetry-browser/pull/396), [semantic-conventions#4011](https://github.com/open-telemetry/semantic-conventions/pull/4011)) and the browser-native instrumentation base ([#278](https://github.com/open-telemetry/opentelemetry-browser/pull/278), merged 24 October).

**1 October 2026.** The browser conventions PR moved from the browser repo to the new client-side registry ([#14](https://github.com/open-telemetry/semantic-conventions-client-side/pull/14), merged 15 October). Actions: an issue for migration documentation, and one to discuss whether a span-based document-load instrumentation is still needed.

**17 September 2026.** By default, the SDK will not record telemetry about its own export requests; a debug mode may allow it later. [#482](https://github.com/open-telemetry/opentelemetry-browser/pull/482) implements this and is still open.

**3 September 2026.** Browser conventions use snake_case keys, converting names that come from browser APIs and libraries (for example `navigationType` from web-vitals). You can see this on the wire in [part 1](/blog/otel-browser-state-2026-10/#what-the-collector-printed).

Earlier decisions that still shape the packages: the XHR span starts at `send()` and keeps no span events (13 August 2026); `quickStartBrowserSdk` should turn sessions on by default (16 July 2026, still not the case in browser-sdk 0.6.0, whose `quickStartBrowserSdk` adds no session processors); and in July 2026 Trent Mick asked to make the Browser SDK the replacement for `WebTracerProvider` so that `sdk-trace-web` could be deprecated, which OTel JS 3.0 then did.

## How to follow it in an hour a week

This is the routine we use for this series. It needs no account except GitHub.

1. **Thursday, after the call:** read the newest entry in the [notes](https://docs.google.com/document/d/1G3yBAV5SzWBO3mmsBUos5bsn4yxsqkS1MLWl1urVojQ). Open every linked issue and PR, because the notes are only pointers.
2. **Releases:** subscribe to the [browser repo releases feed](https://github.com/open-telemetry/opentelemetry-browser/releases.atom) and the [opentelemetry-js releases feed](https://github.com/open-telemetry/opentelemetry-js/releases.atom) in any feed reader. Releases are cut by release-please, so the open "chore: release main" PR is a preview of the next changelog.
3. **npm:** check versions, dates and deprecation flags of the packages you use.

```bash
npm view @opentelemetry/browser-sdk version time.modified dependencies
```

```bash
npm view @opentelemetry/instrumentation-fetch version deprecated
```

4. **Conventions:** watch [semantic-conventions-client-side](https://github.com/open-telemetry/semantic-conventions-client-side/pulls) and PRs touching `model/browser` and `model/session` in [semantic-conventions](https://github.com/open-telemetry/semantic-conventions/pulls).
5. **Breaking changes:** a `!` in a PR title (for example `feat(sdk)!:`) marks a breaking change under the [versioning policy](https://github.com/open-telemetry/opentelemetry-browser/blob/main/VERSIONING.md#marking-breaking-changes). This lists the open ones (on 29 October it printed #532 and #495):

```bash
gh pr list -R open-telemetry/opentelemetry-browser --state open --json number,title --jq '.[] | select(.title | test("!:")) | "#\(.number) \(.title)"'
```

If you want to help, the [contributing guide](https://github.com/open-telemetry/opentelemetry-browser/blob/main/CONTRIBUTING.md) explains how to claim an issue, and PRs now carry an AI-usage disclosure checkbox ([#470](https://github.com/open-telemetry/opentelemetry-browser/pull/470)). Bring an agenda item to the doc before Thursday; the SIG reads it in order.

## What to watch next

- **Document load.** One decision per meeting starts with it ([#327](https://github.com/open-telemetry/opentelemetry-browser/issues/327), [#504](https://github.com/open-telemetry/opentelemetry-browser/pull/504)). It decides whether a page load can be the first span of a trace that continues on your server.
- **The JS 3.x move** for the browser packages ([#525](https://github.com/open-telemetry/opentelemetry-browser/pull/525)), and the deprecation sweep of the classic packages ([#209](https://github.com/open-telemetry/opentelemetry-browser/issues/209)).
- **Sessions on by default** in the quick start, and session start and end events.
- **The OpenTelemetry Demo** moving its frontend to the browser packages: the first large public example.
- **Mobile.** Sessions and conventions are being aligned across browser, Android and iOS in the Client Instrumentation SIG and the client-side registry. We will cover that alignment in this series.
