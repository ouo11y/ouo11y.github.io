## Why Sloth

Three ways to get burn-rate alerts into Prometheus:

- **By hand.** For one SLO, the rules are not hard: [part 3](/blog/slo-burn-rate-alerts/) has the logic. For two SLOs with seven windows each, plus budget and burn-rate series for a dashboard, it is about thirty rules, and one typo in a window silently breaks a page.
- **[Pyrra](https://github.com/pyrra-dev/pyrra)** (2021, Apache 2.0) generates the same multi-burn-rate alerts and is built around a web UI that lists SLOs, budgets and burn rates. It runs as a Kubernetes operator, or as a process next to Prometheus that reads SLO files from a directory.
- **[Sloth](https://github.com/slok/sloth)** (2021, Apache 2.0) generates the rules from a short YAML spec. It is first a CLI that writes a plain rules file; it also has a Kubernetes operator and, since v0.15 (October 2025), a `sloth server` command with a web UI, which we did not try. It reads [OpenSLO](https://openslo.com/) specs as well as its own, and has plugins for common SLIs.

We chose **Sloth** for this series because its output is one ordinary Prometheus rules file, made by a command you can run in CI. Nothing new runs in production: the file works with any Prometheus-compatible ruler, it can be reviewed in a pull request like any other config, and you can read every rule it made. If the UI is what you want most, compare Pyrra's with Sloth's newer one; if you need neither tool, the generated file below is also a good template for writing rules by hand.

### The service

The shop is about 120 lines of Python with no dependencies (`app/shop.py` in the download). It serves `GET /products` and `POST /checkout`, sleeps 10 to 80 ms per request, and counts every request in one histogram named after the OpenTelemetry HTTP convention `http.server.request.duration`. Prometheus spells it with underscores and a unit suffix, as in the spec below, and its labels are `http_route` and `http_response_status_code`. Two extra endpoints make the demo work. `/admin/fault` makes a share of requests fail or slow down, and `/alerts` receives Alertmanager's webhook and prints each alert to the log.

If your service is instrumented with an OpenTelemetry SDK and its metrics reach Prometheus through the collector, you get the same metric with the same labels, and the spec below works unchanged.

## The SLO spec

Two SLOs on the checkout route, over Sloth's default window of 30 days: availability at 99.5% and latency at 99% under 250 ms. The latency SLO counts slow requests as all requests minus those in the `le="0.25"` bucket, which is why the histogram has a bucket at exactly 250 ms ([part 2](/blog/slo-choosing-slis/) explains why thresholds beat percentiles).

```yaml title="slos/tiny-shop.yaml"
version: "prometheus/v1"
service: "tiny-shop"
labels:
  owner: "shop-team"
slos:
  - name: "checkout-availability"
    objective: 99.5
    description: "99.5% of checkout requests in 30 days do not fail with a 5xx."
    sli:
      events:
        # `or vector(0)`: until the first 5xx there is no error series at all, and the SLI
        # would be "no data" instead of 100%.
        error_query: |
          sum(rate(http_server_request_duration_seconds_count{job="shop",http_route="/checkout",http_response_status_code=~"5.."}[{{.window}}]))
          or vector(0)
        total_query: sum(rate(http_server_request_duration_seconds_count{job="shop",http_route="/checkout"}[{{.window}}]))
    alerting:
      name: CheckoutAvailability
      labels:
        category: availability
      annotations:
        summary: "Checkout is burning its availability error budget."
      page_alert:
        labels:
          severity: page
      ticket_alert:
        labels:
          severity: ticket

  - name: "checkout-latency"
    objective: 99
    description: "99% of checkout requests in 30 days finish in 250 ms or less."
    sli:
      events:
        # Slow = all requests minus the ones in the 250 ms bucket.
        error_query: |
          sum(rate(http_server_request_duration_seconds_count{job="shop",http_route="/checkout"}[{{.window}}]))
          -
          sum(rate(http_server_request_duration_seconds_bucket{job="shop",http_route="/checkout",le="0.25"}[{{.window}}]))
        total_query: sum(rate(http_server_request_duration_seconds_count{job="shop",http_route="/checkout"}[{{.window}}]))
    alerting:
      name: CheckoutLatency
      labels:
        category: latency
      annotations:
        summary: "Checkout is burning its latency error budget."
      page_alert:
        labels:
          severity: page
      ticket_alert:
        labels:
          severity: ticket
```

`{{.window}}` is filled in by Sloth, once per alert window. The `or vector(0)` is there because of something we hit on our first run; see [what surprised us](#what-surprised-us).

## Generate the rules

```bash
docker run --rm -v "$PWD:/work" -w /work ghcr.io/slok/sloth:v0.16.0 generate -i slos/tiny-shop.yaml -o prometheus/rules/tiny-shop.rules.yml
```

Sloth logs that it loaded the 30-day window and its plugins, and writes 433 lines: three groups per SLO.

- **SLI recordings**: the error ratio over 5m, 30m, 1h, 2h, 6h, 1d and 3d, and over the 30 days.
- **Meta recordings**: the objective, the budget, the current and 30-day burn rate, and the budget left, which the dashboard draws.
- **Alerts**: one page rule and one ticket rule per SLO.

The series you will query most, each labelled with `sloth_slo`:

```text
slo:sli_error:ratio_rate5m      # and 30m, 1h, 2h, 6h, 1d, 3d, 30d
slo:current_burn_rate:ratio     # burn rate over the last 5 minutes
slo:period_error_budget_remaining:ratio
```

This is the page rule it made for availability. Compare it with the table in part 3: the 1h and 5m windows at 14.4×, or the 6h and 30m windows at 6×, with no `for:`.

```yaml title="prometheus/rules/tiny-shop.rules.yml (excerpt)"
  - alert: CheckoutAvailability
    expr: |
      (
          max(slo:sli_error:ratio_rate5m{sloth_id="tiny-shop-checkout-availability", sloth_service="tiny-shop", sloth_slo="checkout-availability"} > (14.4 * 0.005)) without (sloth_window)
          and
          max(slo:sli_error:ratio_rate1h{sloth_id="tiny-shop-checkout-availability", sloth_service="tiny-shop", sloth_slo="checkout-availability"} > (14.4 * 0.005)) without (sloth_window)
      )
      or
      (
          max(slo:sli_error:ratio_rate30m{sloth_id="tiny-shop-checkout-availability", sloth_service="tiny-shop", sloth_slo="checkout-availability"} > (6 * 0.005)) without (sloth_window)
          and
          max(slo:sli_error:ratio_rate6h{sloth_id="tiny-shop-checkout-availability", sloth_service="tiny-shop", sloth_slo="checkout-availability"} > (6 * 0.005)) without (sloth_window)
      )
    labels:
      category: availability
      severity: page
      sloth_severity: page
```

The ticket rule has the same shape with 2h and 1d at 3×, or 6h and 3d at 1×. Check the file before Prometheus loads it:

```bash
docker run --rm -v "$PWD/prometheus:/etc/prometheus:ro" --entrypoint promtool quay.io/prometheus/prometheus:v3.15.1 check rules /etc/prometheus/rules/tiny-shop.rules.yml
```

## Prove when the page fires

A live demo cannot show what happens after three days of history, and that is the case that matters. `promtool test rules` can: it plays made-up series through the rules on a virtual clock. Our test feeds three clean days of checkouts (400 good requests a minute), then adds 100 failing requests a minute: 20% of checkouts fail, a burn rate of 40× on a 99.5% SLO.

Part 3's identity says the 1-hour window crosses 14.4× once 2% of the budget is gone. Here the 1-hour error ratio is 100·t ÷ (24,000 + 100·t) after *t* minutes, which passes 7.2% (14.4 × 0.5%) at t ≈ 18.6. So: no alert at minute 18, a page at minute 20.

```yaml title="prometheus/tests/tiny-shop.test.yml"
rule_files:
  - ../rules/tiny-shop.rules.yml
evaluation_interval: 1m
tests:
  - interval: 1m
    input_series:
      - series: 'http_server_request_duration_seconds_count{job="shop",http_route="/checkout",http_response_status_code="200"}'
        values: '0+400x4500'
      - series: 'http_server_request_duration_seconds_count{job="shop",http_route="/checkout",http_response_status_code="503"}'
        values: '0x4320 100+100x180'
      - series: 'http_server_request_duration_seconds_bucket{job="shop",http_route="/checkout",le="0.25"}'
        values: '0+500x4500'
    alert_rule_test:
      # 18 minutes in: the 5m window is far over 14.4x, the 1h window is not there yet.
      - eval_time: 4338m
        alertname: CheckoutAvailability
        exp_alerts: []
      # 20 minutes in: the 1h window is over 14.4x too, and the page fires.
      # (It crosses at about 18.6 minutes; recording and alert groups run on their own clocks.)
      - eval_time: 4340m
        alertname: CheckoutAvailability
        exp_alerts:
          - exp_labels:
              alertname: CheckoutAvailability
              category: availability
              owner: shop-team
              severity: page
              sloth_id: tiny-shop-checkout-availability
              sloth_service: tiny-shop
              sloth_severity: page
              sloth_slo: checkout-availability
            exp_annotations:
              summary: Checkout is burning its availability error budget.
              title: (page) tiny-shop checkout-availability SLO error budget burn rate is too fast.
```

```bash
docker run --rm -v "$PWD/prometheus:/etc/prometheus:ro" --entrypoint promtool quay.io/prometheus/prometheus:v3.15.1 test rules /etc/prometheus/tests/tiny-shop.test.yml
```

```text
  SUCCESS
```

It takes about 20 seconds, because promtool evaluates 34 rules for every minute of three days. We first wrote the test for minute 19 and it passed on some runs and failed on others: at that minute the 1-hour ratio has only just crossed, and whether the alert sees it depends on whether its rule group runs before or after the recording group in the same minute. Alerts read recording rules that may be one evaluation old. Test a minute or two away from the edge.

Put this test in CI next to `sloth validate -i slos/` (which exits 0 on our spec), and nobody can change a window or a threshold without seeing which alerts move.

## Route pages and tickets

Sloth sets `severity: page` or `severity: ticket`. Alertmanager decides where they go. In the demo, both receivers are the shop's own webhook so you can watch them in the log; in real life one is a pager and the other a ticket queue.

```yaml title="alertmanager/alertmanager.yml"
route:
  receiver: ticket
  group_by: [alertname, sloth_slo, severity]
  group_wait: 10s
  group_interval: 1m
  repeat_interval: 4h
  routes:
    - matchers: [severity="page"]
      receiver: page

receivers:
  - name: page
    webhook_configs:
      - url: http://shop:8080/alerts
        send_resolved: true
  - name: ticket
    webhook_configs:
      - url: http://shop:8080/alerts
        send_resolved: true

inhibit_rules:
  # While a page is firing for an SLO, hold back the ticket for the same SLO.
  - source_matchers: [severity="page"]
    target_matchers: [severity="ticket"]
    equal: [sloth_slo]
```

The inhibit rule is the answer to part 3's hard outage: a fast burn fires every condition, but the person who was paged does not also need a ticket for the same SLO.

Every line in that table is explained by part 3, once you remember that this Prometheus was ten minutes old:

- **The ticket came first, after 40 seconds.** Its "3-day" and "6-hour" windows held ten minutes of data, so they behaved like ten-minute windows. In the promtool test, with three days of history, the same burn takes about 88 minutes to file a ticket.
- **The page came after 2 minutes 55 seconds, from the 6h and 30m pair.** Both windows held the same 13 minutes, and both crossed 6× together. With a real 6-hour history it is the 1-hour pair that fires, after 20 minutes, as the test shows.
- **After the fix, the 5-minute burn was back to 0 within 5 minutes, but the page stayed on for 26 minutes.** The page was held by the 6h and 30m pair, so its reset time is the 30-minute short window: it cleared once most of the burst had left the last 30 minutes. A page that fired from the 1-hour pair clears with its 5-minute window instead.
- **The latency fault filed a ticket and did not page.** 15% slow requests on a 99% SLO is a burn of 15×. The 5-minute window peaked at 16×, over 14.4×, but the 1-hour window never got there, and 10 minutes of it was 5× in the 30-minute window, under 6×. That is the "short blip" case from part 3: worth a look in working hours, not at night.
- **Inhibition worked, but late.** While the page fired, `amtool alert query --inhibited` listed the availability ticket as `suppressed`. The ticket notification had already gone out two minutes before the page existed: an inhibit rule holds back notifications only while the source alert is firing.

## The dashboard

The dashboard JSON is in `grafana/dashboards/slo.json` in the download. Sloth's author also publishes a fuller [SLO detail dashboard](https://grafana.com/grafana/dashboards/14348) for these series on grafana.com; ours is smaller so that every panel's query can be read in one line.

## What surprised us

- **No errors meant no data, not 100%.** On our first run the SLI panels said "No data" until the first `503`: a series that has never been seen does not exist in Prometheus, so `sum(rate(...5xx...))` returned nothing and the whole ratio with it. Hence the `or vector(0)` in the spec. The latency SLO does not need it, because its error query subtracts two series that always exist.
- **The 30-day budget is meaningless on day one.** "Error budget left" went to −1,654% during our run. Sloth computes the 30-day error ratio as the mean of the 5-minute ratios that exist, so with 40 minutes of history, a 10-minute burst is a quarter of "30 days". Trust the budget once a whole window of data exists. Because it averages 5-minute ratios, a busy 5 minutes and a quiet one also count the same: close to a window-based SLI from part 2, not a pure request count.
- **Long windows are only as long as your history.** Every early alert above came from that. After a Prometheus restart with lost data, or on a new service, expect tickets and pages sooner than the tables say.
- **Alerts read recording rules that may be one evaluation old.** The flaky test at minute 19 taught us that.

## On Mimir, Thanos and other rulers

The generated file is a standard Prometheus rule file, so it should load into any ruler that reads that format: [Mimir's ruler](https://grafana.com/docs/mimir/latest/references/architecture/components/ruler/) (for example with `mimirtool rules load`), Thanos Ruler, or VictoriaMetrics' vmalert. We ran it only on Prometheus `v3.15.1`; we did not test the others here. Two things to check on a ruler: that it evaluates rule groups often enough for the 5-minute window (Sloth's groups use the global evaluation interval), and that a query over `[30d]` and `[3d]` is allowed by its limits.

## What to take away

- Write SLOs as a spec and generate the rules. Review the spec in pull requests, and keep a promtool test that pins when the page fires.
- Pages come from fast burns and clear with their short window. Tickets come from slow burns and stay for hours. Route them to different places, and inhibit tickets while a page for the same SLO fires.
- Give a new Prometheus a few days before you believe its long windows or its 30-day budget.
- Initialise your error series, or add `or vector(0)`, so a perfect service shows 100% and not "No data".
