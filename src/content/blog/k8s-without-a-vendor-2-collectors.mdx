## 1. A three-node cluster with kind

We use [kind](https://kind.sigs.k8s.io/) rather than minikube for three reasons. It runs on the Docker you already have. A multi-node cluster is three lines of YAML. And the node names stay stable (`blog-k8s-worker`, `blog-k8s-worker2`), which matters for the node level in the dashboards. minikube can run several nodes too; nothing below depends on kind except this file.

Three nodes, not one, because several things in this post only go wrong when pods sit on different nodes.

```yaml title="kind.yaml"
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: blog-k8s
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30300
        hostPort: 3300
  - role: worker
  - role: worker
```

The port mapping lets you reach Grafana at `localhost:3300` later without a port-forward.

kind create cluster --config kind.yaml

## 3. The stores: Prometheus, Loki, Tempo

All three take OTLP directly, so the collectors need no Prometheus remote-write or Loki-specific exporter.

```bash
kubectl create namespace observability
```

### Prometheus

Prometheus 3 has an OTLP receiver behind the `web.enable-otlp-receiver` flag. Two settings in the `otlp` block decide how OpenTelemetry data looks once it is stored:

- **`translation_strategy`** turns OpenTelemetry names into Prometheus names. <code style={{overflowWrap: 'anywhere'}}>UnderscoreEscapingWithSuffixes</code> replaces dots with underscores and adds the unit and `_total`, so `k8s.pod.cpu.time` (a counter in seconds) becomes <code style={{overflowWrap: 'anywhere'}}>k8s_pod_cpu_time_seconds_total</code>. This is the classic behaviour and works with every Grafana version. Prometheus 3 can also keep the dots, but then every query has to quote the name.
- **`promote_resource_attributes`** turns resource attributes into labels. Without it, `k8s.pod.name` and the rest go only to a separate `target_info` series, and every query needs a join. We promote the `k8s.*` names the dashboards filter on.

The chart's own scrape jobs are switched off: the collectors push everything.

```yaml title="prometheus.yaml"
# Prometheus 3 as the metrics store. It takes OTLP directly at /api/v1/otlp.
alertmanager:
  enabled: false
kube-state-metrics:
  enabled: false
prometheus-node-exporter:
  enabled: false
prometheus-pushgateway:
  enabled: false

server:
  extraFlags:
    - web.enable-lifecycle
    - web.enable-otlp-receiver
  retention: 2d
  persistentVolume:
    enabled: false
  tsdb:
    out_of_order_time_window: 30m
  otlp:
    translation_strategy: UnderscoreEscapingWithSuffixes
    promote_resource_attributes:
      - k8s.cluster.name
      - k8s.node.name
      - k8s.namespace.name
      - k8s.deployment.name
      - k8s.statefulset.name
      - k8s.daemonset.name
      - k8s.replicaset.name
      - k8s.job.name
      - k8s.cronjob.name
      - k8s.pod.name
      - k8s.pod.uid
      - k8s.container.name
      - k8s.volume.name
      - service.namespace
      - service.name

# Nothing is scraped by Prometheus itself: the collectors push everything.
scrapeConfigs:
  kubernetes-api-servers: {enabled: false}
  kubernetes-nodes: {enabled: false}
  kubernetes-nodes-cadvisor: {enabled: false}
  kubernetes-service-endpoints: {enabled: false}
  kubernetes-service-endpoints-slow: {enabled: false}
  prometheus-pushgateway: {enabled: false}
  kubernetes-services: {enabled: false}
  kubernetes-pods: {enabled: false}
  kubernetes-pods-slow: {enabled: false}
```

### Loki

One Loki process with its data on the pod's disk. Loki 3 accepts OTLP at `/otlp` and makes some resource attributes into index labels by default, among them `k8s.namespace.name`, `k8s.pod.name`, `k8s.container.name`, `k8s.deployment.name` and `service.name`. The rest, including a log record's trace id, is kept as structured metadata, which is why `allow_structured_metadata` is on.

```yaml title="loki.yaml"
# Loki as one process with its data on the pod's disk. Fine for a laptop, not for production.
deploymentMode: Monolithic
loki:
  auth_enabled: false
  commonConfig:
    replication_factor: 1
  storage:
    type: filesystem
  schemaConfig:
    configs:
      - from: "2026-01-01"
        store: tsdb
        object_store: filesystem
        schema: v13
        index:
          prefix: index_
          period: 24h
  limits_config:
    allow_structured_metadata: true
    volume_enabled: true
  pattern_ingester:
    enabled: true
singleBinary:
  replicas: 1
  persistence:
    enabled: false
read:
  replicas: 0
write:
  replicas: 0
backend:
  replicas: 0
gateway:
  enabled: false
chunksCache:
  enabled: false
resultsCache:
  enabled: false
lokiCanary:
  enabled: false
test:
  enabled: false
```

### Grafana

Grafana gets the three data sources with fixed UIDs (the dashboards in part 3 refer to them), and the links between them:

- **Loki → Tempo:** the `trace_id` derived field reads the trace id from each log record's structured metadata and turns it into an "Open trace" link.
- **Tempo → Loki:** from a span, "Logs for this span" queries Loki for the same pod and namespace, filtered by trace id.
- **Tempo → Prometheus:** from a span, the pod's CPU and memory around that time.

A sidecar loads every ConfigMap labelled `grafana_dashboard=1` as a dashboard. That is how part 3 installs its dashboards.

```yaml title="grafana.yaml"
# Grafana on http://localhost:3300 (kind maps host port 3300 to node port 30300).
service:
  type: NodePort
  nodePort: 30300

# A laptop-only shortcut: no login, every visitor is an admin.
grafana.ini:
  auth.anonymous:
    enabled: true
    org_role: Admin
  auth:
    disable_login_form: true

# Load every ConfigMap labelled grafana_dashboard=1 as a dashboard.
sidecar:
  dashboards:
    enabled: true
    label: grafana_dashboard
    labelValue: "1"
    searchNamespace: ALL
    folderAnnotation: grafana_folder
    provider:
      foldersFromFilesStructure: true

datasources:
  datasources.yaml:
    apiVersion: 1
    datasources:
      - name: Prometheus
        uid: prometheus
        type: prometheus
        url: http://prometheus-server.observability.svc
        isDefault: true
        jsonData:
          exemplarTraceIdDestinations:
            - name: trace_id
              datasourceUid: tempo
      - name: Loki
        uid: loki
        type: loki
        url: http://loki.observability.svc:3100
        jsonData:
          derivedFields:
            # OTLP logs keep the trace id as structured metadata, not in the line.
            - name: trace_id
              matcherType: label
              matcherRegex: trace_id
              url: "$${__value.raw}"
              datasourceUid: tempo
              urlDisplayLabel: Open trace
      - name: Tempo
        uid: tempo
        type: tempo
        url: http://tempo.observability.svc:3200
        jsonData:
          tracesToLogsV2:
            datasourceUid: loki
            spanStartTimeShift: -5m
            spanEndTimeShift: 5m
            filterByTraceID: true
            tags:
              - key: k8s.namespace.name
                value: k8s_namespace_name
              - key: k8s.pod.name
                value: k8s_pod_name
          tracesToMetrics:
            datasourceUid: prometheus
            spanStartTimeShift: -5m
            spanEndTimeShift: 5m
            tags:
              - key: k8s.pod.name
                value: k8s_pod_name
            queries:
              - name: Pod CPU
                query: 'sum(rate(k8s_pod_cpu_time_seconds_total{$$__tags}[1m]))'
              - name: Pod memory
                query: 'sum(k8s_pod_memory_working_set_bytes{$$__tags})'
          nodeGraph:
            enabled: true
```

## 4. The collectors: opentelemetry-kube-stack

The chart installs the OpenTelemetry Operator and asks it to run collectors, described as `OpenTelemetryCollector` resources. Its defaults already follow the blueprint: one DaemonSet with the `kubeletMetrics`, `hostMetrics`, `logsCollection`, `kubernetesAttributes`, `clusterMetrics` and `kubernetesEvents` presets, and leader election for the last two. Every collector only has a `debug` exporter until you add your own.

Here is the values file we ended with. The sections after it explain the parts that differ from the defaults.

```yaml title="kube-stack.yaml"
# opentelemetry-kube-stack 0.26.0: the OpenTelemetry Operator plus two collectors.
clusterName: blog-k8s
resourceAttributes:
  k8s.cluster.name: blog-k8s

# The operator's webhook needs a TLS certificate. Let the chart make one
# instead of installing cert-manager.
opentelemetry-operator:
  admissionWebhooks:
    certManager:
      enabled: false
    autoGenerateCert:
      enabled: true

# Every collector inherits these exporters: OTLP to the three stores.
defaultCRConfig:
  config:
    exporters:
      otlp_http/prometheus:
        endpoint: http://prometheus-server.observability.svc/api/v1/otlp
      otlp_http/loki:
        endpoint: http://loki.observability.svc:3100/otlp
      otlp_grpc/tempo:
        endpoint: tempo.observability.svc:4317
        tls:
          insecure: true

collectors:
  # The agent: one per node. Reads its own node's kubelet, host, pod logs and
  # annotated Prometheus endpoints, and receives OTLP from the pods on its node.
  daemon:
    scrape_configs_file: ""
    tolerations:
      - operator: Exists
    presets:
      logsCollection:
        enabled: true
      kubeletMetrics:
        enabled: true
      hostMetrics:
        enabled: true
      kubernetesAttributes:
        enabled: true
      prometheus:
        podAnnotations:
          enabled: true
      # Cluster-wide receivers run in the "cluster" collector below.
      clusterMetrics:
        enabled: false
      kubernetesEvents:
        enabled: false
      # Resource detection describes the collector itself: its pod, namespace
      # and node. On an agent that reports on other things it fills gaps with
      # the wrong values. Every receiver here already says where its data is from.
      resourceDetection:
        env:
          enabled: false
        k8s_api:
          enabled: false
    config:
      processors:
        # host_metrics and pod-annotation scrapes do not say which node they
        # came from. This agent only reads its own node, so name it. insert
        # never overwrites a k8s.node.name a receiver already set.
        resource/node:
          attributes:
            - key: k8s.node.name
              value: ${env:OTEL_K8S_NODE_NAME}
              action: insert
        # The sample app writes JSON lines with trace_id and span_id. Copy them
        # into the log record's own trace context so Loki and Grafana see them.
        transform/trace_ids:
          error_mode: ignore
          log_statements:
            - conditions:
                - IsMatch(log.body, "^\\{.*\"trace_id\"")
              statements:
                - set(log.cache, ParseJSON(log.body))
                - set(log.trace_id.string, log.cache["trace_id"]) where log.cache["trace_id"] != nil
                - set(log.span_id.string, log.cache["span_id"]) where log.cache["span_id"] != nil
      service:
        pipelines:
          # Listing processors replaces the chart's list; the presets still
          # put k8s_attributes first and resource/global last.
          metrics:
            processors: [resource/node, resource/hostname, batch]
            exporters: [otlp_http/prometheus]
          logs:
            processors: [resource/node, resource/hostname, transform/trace_ids, batch]
            exporters: [otlp_http/loki]
          traces:
            processors: [resource/node, resource/hostname, batch]
            exporters: [otlp_grpc/tempo]

  # The cluster collector: one replica. Watches the API server for object state
  # (k8s_cluster) and events (k8s_objects). Its k8s_attributes sees every pod,
  # so pod metrics get their deployment, statefulset or daemonset name.
  cluster:
    enabled: true
    suffix: cluster
    mode: deployment
    replicas: 1
    presets:
      clusterMetrics:
        enabled: true
      kubernetesEvents:
        enabled: true
      kubernetesAttributes:
        enabled: true
    config:
      receivers:
        # Merged into the preset's k8s_cluster receiver. Why a container last
        # stopped (OOMKilled, Error...) and what it is waiting on now.
        k8s_cluster:
          metrics:
            k8s.container.status.reason:
              enabled: true
          resource_attributes:
            k8s.container.status.last_terminated_reason:
              enabled: true
      processors:
        batch: {}
        # Events have no service. Name them so Loki indexes them under one
        # service_name instead of "unknown_service".
        resource/events:
          attributes:
            - key: service.name
              value: k8s-events
              action: insert
      service:
        pipelines:
          metrics:
            receivers: []
            processors: [batch]
            exporters: [otlp_http/prometheus]
          logs:
            receivers: []
            processors: [resource/events, batch]
            exporters: [otlp_http/loki]
```

### No cert-manager

The Operator's admission webhook needs a TLS certificate. The chart's default is to ask cert-manager for one, and the install fails with `no matches for kind "Certificate"` if cert-manager is not there. `autoGenerateCert` makes Helm generate a certificate instead. That has a side effect we come back to in step 5.

### Fix 1: resource detection names the collector, not the data

The chart turns on the `resource_detection` processor with the `env` and `k8s_api` detectors on the agent. The `env` detector reads the collector's own `OTEL_RESOURCE_ATTRIBUTES`, which the chart fills with the collector pod's name, namespace and node. With `override: false` it only fills attributes that are missing, which sounds safe. It is not: node metrics have no `k8s.pod.name`, so they got the collector's. This is what Prometheus held for a node condition with the defaults:

```text
k8s_node_condition_ready{k8s_cluster_name="blog-k8s", k8s_namespace_name="otel",
  k8s_node_name="blog-k8s-worker2", k8s_pod_name="kube-stack-daemon-collector-slwst"} 1
```

That node is not in the `otel` namespace, and the pod named is a collector on a different node. Any query that groups by namespace or pod counts it in the wrong place. With only the `k8s_api` detector left, deployment metrics still got the elected agent's node name. Resource detection is meant to describe the process that runs it, so we turned it off on the agent. The receivers already say where their data came from, and `resourceAttributes` sets `k8s.cluster.name` on everything.

Two receivers do not name their node: `host_metrics` and the Prometheus scrape of annotated pods. The `resource/node` processor inserts the agent's own node name, which is right because an agent only reads its own node. `insert` never overwrites a value a receiver set.

### Fix 2: cluster metrics need a cluster-wide view

With the blueprint's layout, `k8s_cluster` runs inside whichever agent holds the lease. That agent's `k8s_attributes` processor only watches pods on its own node, to keep each agent's memory small. So `k8s.pod.phase` and the other per-pod cluster metrics only got their `k8s.deployment.name` (or StatefulSet, or DaemonSet) when the pod happened to share a node with the leader. A dashboard that counts running pods per Deployment would show `shop-api` with one pod instead of two, and the number would change whenever the lease moved. You could remove the node filter from every agent, but then each agent watches every pod in the cluster. We used the chart's second collector instead, the layout the blueprint offers for clusters without leader election: a one-replica Deployment named `cluster` that runs `k8s_cluster` and `k8s_objects`, with a `k8s_attributes` that sees every pod. It keeps the leader-election extension, so you can raise `replicas` to 2 for failover.

The same collector turns on two optional parts of `k8s_cluster`: the `k8s.container.status.reason` metric and the <code style={{overflowWrap: 'anywhere'}}>k8s.container.status.last_terminated_reason</code> resource attribute. Together they say why a container is waiting and why it last stopped, for example `OOMKilled`. Part 3 uses both.

### Smaller things in the file

- **Listing processors replaces the chart's list.** Once you write `processors:` for a pipeline, the chart's defaults for that pipeline are gone. The presets still put `k8s_attributes` first and `resource/global` last.
- **`transform/trace_ids`.** The sample app writes JSON log lines that carry `trace_id` and `span_id`. This OTTL statement copies them into the log record's own trace context, so Loki stores them as structured metadata and Grafana can link the line to its trace. An app that sends logs over OTLP with an OpenTelemetry logging bridge does not need it.
- **`resource/events`.** Kubernetes events have no service, so Loki filed them under `unknown_service`. We name them `k8s-events`.
- **The `container.image.tag` warning.** Collector 0.162.0 logs that `k8s_attributes` will not emit `container.image.tag` because of the <code style={{overflowWrap: 'anywhere'}}>processor.k8sattributes.DontEmitV0K8sConventions</code> feature gate; it emits `container.image.tags` instead. The chart still asks for the old name. It is harmless.
- **`hostmetrics` on kind** reads the Docker VM's kernel, so every node reports the same 10 CPUs, the same load (including every other container on that VM) and the VM's uptime. On real nodes each agent sees its own machine.
- **A pod with an init container briefly has two series.** While the Operator's init container runs, `k8s_attributes` names it as the pod's container on pod-level metrics. Once the app starts, a second series appears without it. The old one stays visible in Prometheus for five minutes, so a naive `count(k8s_pod_phase == 1)` shows the pod as both Pending and Running. The dashboards in part 3 take the newest value per pod.

## 5. An app with OpenTelemetry

The sample app is two Node.js services and a load generator. `shop-web` calls `shop-api` for a price. `shop-api` is slow for one SKU, fails 5 % of requests, and keeps every response in a cache that never shrinks, so it runs out of memory about every 25 minutes. That gives part 3 something to find. The code lives in a ConfigMap and runs on the stock `node:24-slim` image, so there is nothing to build.

There is no OpenTelemetry code in the app. The `Instrumentation` resource tells the Operator what to inject, and the annotation <code style={{overflowWrap: 'anywhere'}}>instrumentation.opentelemetry.io/inject-nodejs</code> on each pod asks for it. The Operator's webhook then adds an init container that copies the Node.js auto-instrumentation into the pod, and sets `NODE_OPTIONS`, the exporter endpoint and resource attributes (`k8s.pod.name`, `k8s.deployment.name` and more). The one line of logging code reaches the injected OpenTelemetry API to put the trace id on each log line.

### Fix 3: pods created during a Helm upgrade are not instrumented

This one cost us the most time. Each `helm upgrade` of the kube-stack chart generates a new webhook certificate (that is what `autoGenerateCert` does). The webhook configuration gets the new CA at once. The Operator keeps serving the old certificate until the kubelet refreshes the mounted Secret, which took about a minute for us. The webhook's `failurePolicy` is `Ignore`, so during that minute the API server lets everything through without asking the Operator:

<Sequence
  actors={['You', 'API server', 'Operator webhook']}
  caption="What happened to a pod created right after helm upgrade."
  steps={[
    { from: 0, to: 1, label: 'helm upgrade', note: 'new CA in the webhook configuration' },
    { from: 0, to: 1, label: 'create pod / Instrumentation' },

    { from: 2, to: 1, label: 'TLS: bad certificate', tone: 'bad' },

/>

We saw two symptoms. Pods started without the init container and sent no telemetry, with no error anywhere except `tls: bad certificate` in the Operator's log. Worse, an `Instrumentation` created in that window never got its defaults, so every later pod was rejected with <code style={{overflowWrap: 'anywhere'}}>spec.initContainers[0].image: Required value</code>.

What works:

1. Install or upgrade kube-stack, then wait until the Operator's log has no new `bad certificate` lines before you create instrumented pods.
2. If `.spec.nodejs.image` on your `Instrumentation` is empty, delete it and apply it again.
3. Restart pods that are missing the init container: <code style={{overflowWrap: 'anywhere'}}>kubectl -n shop rollout restart deployment/shop-api deployment/shop-web</code>.

With cert-manager instead of `autoGenerateCert`, the certificate does not change on every upgrade.

### Two settings in the Instrumentation

- **<code style={{overflowWrap: 'anywhere'}}>OTEL_METRIC_EXPORT_INTERVAL: "15000"</code>.** The SDK exports metrics every 60 seconds by default. Grafana's `$__rate_interval` on a 15-second scrape interval is one minute, which then holds one point, and `rate()` needs two. Request-rate panels stayed empty until we exported every 15 seconds.
- **`OTEL_NODE_RESOURCE_DETECTORS`.** The default set includes cloud detectors that try metadata endpoints. On a laptop they time out and print `MetadataLookupWarning`.
