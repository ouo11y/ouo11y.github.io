A user clicks **Buy**. Two hundred and seventy-eight milliseconds later the page says *paid*. In between, the click went through a browser, an HTTP API, Redis, PostgreSQL, a message queue, a worker in another language, PostgreSQL again and Redis again. When that click takes four seconds instead, which hop was it?

This series builds that system on your laptop and answers the question with OpenTelemetry. By the end of this part you will click Buy, copy one `trace_id` from the page, and open from it the whole journey in Tempo, the log lines every service wrote for that click in Loki, and the latency graph in Mimir with a dot on it that opens the same trace.

The four parts:

1. **One click, three signals** (this post): the system, and how traces, logs and metrics find each other.
2. **Queues**: carrying context through a message, span links or parent/child, and the metrics that tell you a queue is in trouble.
3. **Databases and Redis**: the stable `db.*` conventions, what gets recorded as query text, connection pools, and finding the slow query from a slow click.
4. **Exemplars in depth**: every hop between a histogram bucket and a trace, and the ways we broke each one.

## Where "one trace across everything" came from

The idea that one request carries an ID through every process it touches is older than OpenTelemetry. Google described it in the [Dapper paper](https://research.google/pubs/dapper-a-large-scale-distributed-systems-tracing-infrastructure/) in 2010: a trace is a tree of spans, every RPC passes the trace and parent span IDs along, and the tree is put back together later from what each service recorded. Twitter's Zipkin (2012) and Uber's Jaeger (2015) brought the model to everyone else.

What was missing for years was an agreed header. Every tracer had its own (`X-B3-TraceId`, `uber-trace-id`, …), so a trace broke at the first service that used a different library. The W3C [Trace Context](https://www.w3.org/TR/trace-context/) recommendation fixed that in February 2020 with one header, `traceparent`, which carries a 16-byte trace ID, an 8-byte parent span ID and a sampled flag. OpenTelemetry, formed in 2019 from the merger of OpenTracing and OpenCensus, uses it by default.

Logs and metrics joined later. The OpenTelemetry [log data model](https://opentelemetry.io/docs/specs/otel/logs/data-model/) gives every log record a `TraceId` and `SpanId` field, so a log line written inside a span carries that span's identity without you formatting it into the message. For metrics, an aggregated number cannot carry the ID of every request it counted, so OpenTelemetry borrowed [exemplars](https://opentelemetry.io/docs/specs/otel/metrics/data-model/#exemplars) from OpenMetrics: a few sample measurements, each with the trace it came from. Part 4 is about those.

So "end to end" is three agreements: one header between processes, one pair of fields in every log record, and one sampled trace ID on a metric. Most of the work in this post is making sure every hop keeps them.

What one order does:

1. The browser starts a `buy` span and sends `POST /api/orders` with a `traceparent` header.
2. The API looks the product up in Redis (on a miss, in PostgreSQL, then caches it for 30 seconds), inserts the order, publishes a message to the `orders` queue and answers `202`.
3. The worker takes the message, "charges the card", marks the order paid, counts the customer's past orders (a query that is slow on purpose, for part 3) and writes the status to Redis.
4. The browser polls `GET /api/orders/:id` every 250 ms until it reads `paid`, then ends the `buy` span.

Two languages on purpose: a trace that only works when every service uses the same SDK is not end to end. The API is Node.js because that is where most readers start; the worker is Python because, as part 4 shows, the Node.js SDK does not record exemplars yet and the Python one does.

**Why RabbitMQ and not Kafka.** This is a work queue: each order is a job that one worker takes, does and acknowledges. That is RabbitMQ's model (a queue, acknowledgements, redelivery), and it runs as one container with a management API the Collector can read. Kafka is a log: messages stay after they are read, consumers track an offset, and "lag" is the distance between the newest offset and the group's. Pick Kafka when you need replay, many independent readers of the same stream, or partitioned ordering. The tracing in this series works the same way on both, because context rides in message headers either way; part 2 says where the metrics differ.

<Note type="danger" title="The bug that cost us an hour">
OpenTelemetry JS 3.0 changed `BatchSpanProcessor` to take its exporter as an option: `new BatchSpanProcessor({ exporter, scheduledDelayMillis })`. We first wrote the 2.x form, `new BatchSpanProcessor(exporter, options)`. It threw nothing, logged nothing, and exported nothing: the browser recorded spans, `forceFlush()` resolved, and the network tab showed no request to `/v1/traces`. In the page, the processor's `_exporter` was `undefined`. The backend half of the trace still arrived, because `traceparent` was sent; only the browser's own spans were missing. If your browser spans vanish after an upgrade to 3.0, check this first.
</Note>

### Logs: trace_id without formatting it yourself

Neither service puts a trace ID into a log message. The pino instrumentation adds `trace_id`, `span_id` and `trace_flags` to every line written inside a span and also sends each record through the OpenTelemetry logs SDK; Python's logging instrumentation does the same for the standard `logging` module. Both go OTLP to the Collector and on to Loki's native OTLP endpoint, where `trace_id` becomes structured metadata: searchable, but not a label, so it does not create one stream per trace.

The query for one click's logs, from every service:

```bash
curl -s -G http://127.0.0.1:47100/loki/api/v1/query_range \
  --data-urlencode 'query={service_name=~"shop-.+"} | trace_id="58898222c16257cf4a2ab93951a45043"'
```

returned two streams (fields trimmed):

```text
service_name=shop-worker  span_id=dabb9d3488a7bde8  code_function_name=process  code_line_number=95
    order 3000248 paid, customer has 61 orders
service_name=shop-api     span_id=f97f8b5c4492b4ad  scope_name=@opentelemetry/instrumentation-pino
    order accepted
```

Each `span_id` is the span that was current when the line was written: the API's request handler and the worker's `process orders`. Loki's configuration keeps labels to `service_name` and the environment; everything else stays structured metadata:

### Grafana: the links are datasource settings

<E2eFile path="grafana/provisioning/datasources/datasources.yaml" />

Four links, each a few lines:

- **Loki → Tempo**, `derivedFields` with `matcherType: label`: the field is read from structured metadata named `trace_id`, not with a regex over the log line. In Explore, expanding the worker's log line shows a **View trace** link.
- **Tempo → Loki**, `tracesToLogsV2` with `filterByTraceID`: the **Logs for this trace** button on every trace.
- **Tempo → Mimir**, `tracesToMetrics`: from a span to its service's request rate and p95, with `service.name` mapped to the `service_name` label.
- **Mimir → Tempo**, `exemplarTraceIdDestinations`: an exemplar's `trace_id` label becomes **Query with Tempo**.

We clicked each of them in Grafana 13.3.0 with this provisioning.

### Metrics: the dot that opens the trace

The API's request latency histogram is computed in the Collector from spans (the `span_metrics` connector, below), and every bucket keeps a few exemplars. Asking Mimir for exemplars on it:

```bash

  --data-urlencode 'query=traces_span_metrics_duration_bucket{service_name="shop-api"}' \
  --data-urlencode start=$(( $(date +%s) - 300 )) --data-urlencode end=$(date +%s)
```

returned 260 exemplars over 34 series in five minutes, among them:

## The Collector

Three things worth knowing:

- **The `span_metrics` connector** is an exporter of the traces pipeline and a receiver of the metrics pipeline. It turns every span into a call count and a duration histogram per service, span name, kind, status and the dimensions we listed, and it keeps exemplars. Part 4 explains why we need it for the Node.js API.
- **Three receivers pull from the infrastructure**: `rabbitmq` (queue depth, publish and deliver counts, from the management API), `redis` (`INFO`: hits, misses, memory) and `postgresql` (backends, commits, sizes). Parts 2 and 3 use them.
- **Component names changed.** Collector 0.164.0 logs `"otlp" alias is deprecated; use "otlp_grpc" instead`, and the same for `otlphttp` (now `otlp_http`) and `spanmetrics` (now `span_metrics`). The old names still work; the config above uses the new ones.

Tempo and Mimir run as single binaries with local storage. Two lines in Mimir's limits matter for this series: `max_global_exemplars_per_user`, which is 0 by default and drops every exemplar (part 4 shows it), and `promote_otel_resource_attributes`, without which the RabbitMQ queue-depth series have no queue name (part 2).

## What we learned

- One `trace_id` gets you everything only if every hop keeps it: the `traceparent` header on HTTP, the same header inside the AMQP message, the `TraceId` field on every log record, and an exemplar on the metrics.
- Most of that is free with zero-code instrumentation. What is not free is the configuration that lets Grafana jump: four datasource settings, all shown above.
- Three things broke silently on the way, and none of them logged an error: `BatchSpanProcessor` with the 2.x arguments, a healthcheck that checked the wrong socket, and doubled middleware spans from two instrumentations of the same router.

[Part 2](/blog/e2e-observability-2-queues/) takes the message between the API and the worker apart: how the context travels, why the specification prefers span links to parent/child, and what to measure so that a stuck queue pages you before your users do.
