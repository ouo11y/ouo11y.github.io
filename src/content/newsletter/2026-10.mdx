October was a month of things growing up. The Collector's transformation language got a 1.x promise,
OpenTelemetry JavaScript shipped its first major version since 2.0, Go logs went stable, and the
project wrote down when a security fix is allowed to break you. If you only have two minutes, read
the stability chart below and the Release radar.

<Item id="ottl-v1" title="OTTL reaches v1" label="stable" date="2026-10-26"
  why="Most redaction, enrichment, routing and filtering in a Collector is written in OTTL. Those rules now have a compatibility promise: a contrib upgrade should not silently change what they do."

The OpenTelemetry Transformation Language is stable for traces, metrics and logs from
`opentelemetry-collector-contrib` v0.164.0 (26 October). Everything in the language reference is
covered: paths, literals, operators, function calls and `where` clauses. New syntax may arrive in
minor releases, but no standard function will be removed or change its signature incompatibly, and
the Go API stays compatible.

Still experimental: lambda-style functions, new functions (they start in a separate `xottl` module
behind a gate), and profiles support (moved to an `xprofile` module). The transform processor
itself is still beta; the OTel blog names it as the next candidate for stable.

</Item>

  deeper={[
    { label: 'The state of OpenTelemetry in the browser', href: '/blog/otel-browser-state-2026-10/' },
    { label: 'How OpenTelemetry came to be (the OpenTracing shim, and why it is gone)', href: '/blog/how-opentelemetry-came-to-be/' },

Released 20 October. The main changes:

- `sdk-trace-base`, `sdk-trace-node` and `sdk-trace-web` are gone, replaced by a single `@opentelemetry/sdk-trace`.
- The minimum Node.js version is 22.15.0; Node 18 and 20 are no longer supported.
- Packages are built as dual CommonJS and ESM with an `exports` map, so imports into a package's build folder fail.
- The OpenTracing shim, the Jaeger exporter and the Jaeger propagator are removed.
- `@opentelemetry/sdk-logs` is marked stable.
- `LoggerConfig.disabled` becomes `enabled`, to match the spec.

</Item>

<Item id="security-policy" title="Security fixes may now change behavior in minor releases" label="security" date="2026-10-22"
  why="Until now, a minor upgrade of a stable SDK was supposed to change nothing you rely on. Now a narrowly scoped security fix can make it reject input or config it used to accept, or truncate and drop telemetry."
  todo="Read the release notes of minor and patch upgrades of stable SDKs and contrib components, not only majors. The policy requires those notes to say what changed, what is now rejected, and what you need to do."
  sources={[
    { label: 'OTel blog: Strengthening security while preserving API stability', href: 'https://opentelemetry.io/blog/2026/security-versioning-policy/' },
    { label: 'spec PR #5357', href: 'https://github.com/open-telemetry/opentelemetry-specification/pull/5357' },
  ]}>

The specification's versioning rules (merged 20 October, announced 22 October) now let stable SDKs
and contrib components ship a necessary, minimal security fix in a minor or even a patch release,
even when it changes documented behavior or defaults. The examples given are stricter certificate
checks, turning off unsafe protocols, keeping credentials out of telemetry, and limits against
denial of service.

What stays protected: public APIs, configuration parameter names, semantic conventions, and source
and binary compatibility. Stable API packages keep their full guarantees.

</Item>

The OpenTelemetry Java agent 2.32.0 (3 October) is the release candidate for 3.0, which the SIG
targeted for October. In 3.0, the stable database and code conventions become the defaults
(`db.statement` becomes `db.query.text`, `db.system` becomes `db.system.name`, `db.name` becomes
`db.namespace`), and messaging moves to newer, still experimental conventions, which changes span
names and how producer and consumer spans connect. As of 29 October, 2.33.0 and 2.33.1 have shipped
and 3.0 has not.

</Item>

OpenTelemetry Python 1.45.2 (29 October) enforces the metric cardinality limit from the
specification, configurable per view, per reader and in declarative configuration. It also caps
the `traceparent` header at 512 characters during extraction. 1.45.1 (6 October) fixed
quadratic-time parsing of `tracestate` and drops headers over 8192 characters.

</Item>
