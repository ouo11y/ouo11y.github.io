<Item id="obi-1" title="OpenTelemetry eBPF Instrumentation reaches 1.0" label="stable" date="2026-10-30"
  why="OBI gives you request rates, errors, latency and service dependencies for Linux services without touching their code. A 1.0 means configuration and deployment now carry a written compatibility promise, so it is safer to roll out across a fleet."
  todo="If you run OBI on Config v1, migrate with `obi config migrate` and check it with `obi config validate`: v1 still works but is frozen. Compare telemetry in a canary before a broad rollout. If you embed OBI in a Collector, note that its receiver keeps a separate v0 release line."
  sources={[
    { label: 'OTel blog: OBI reaches v1.0.0', href: 'https://opentelemetry.io/blog/2026/obi-v1-release/' },
    { label: 'OBI v1.0.0 release', href: 'https://github.com/open-telemetry/opentelemetry-ebpf-instrumentation/releases/tag/v1.0.0' },
  ]}
  deeper={[{ label: 'Kubernetes observability without a vendor, part 2: the collectors', href: '/blog/k8s-without-a-vendor-2-collectors/' }]}>

OBI v1.0.0 was released on 30 October; the project began as Grafana's donation of Beyla. The
compatibility promise covers Config v2, its generated schema and the documented deployment
interfaces. Telemetry is treated differently: what follows stable conventions stays put (except bug
fixes), what follows conventions still in development can change, and OBI now describes all of it in
a Weaver schema registry with migration notes. Since the early releases it has added MQTT, NATS,
AMQP 1.0, MSSQL, Couchbase, Memcached and Aerospike, route discovery for common Python, Ruby, .NET and
PHP frameworks, trace-log correlation, and opt-in GenAI instrumentation.

</Item>

<Item id="semconv-1-45" title="Semantic conventions v1.45.0: stable RPC, renamed messaging and RPC metadata" label="breaking" date="2026-11-02"
  why="Issue #1 reported RPC stability as merged but unreleased; it is now in a release, so instrumentations will start shipping it. The same release renames attributes many dashboards filter on."
  todo="Search queries and alerts for `rpc.response.status_code` (now `rpc.status_code`), `rpc.request.metadata.*` / `rpc.response.metadata.*` (now `header` and `trailer`), `messaging.system` (now `messaging.system.name`), `messaging.kafka.*` (now `kafka.*`), `db.client.connection.max` (now `.limit`) and `system.memory.state=free|buffers|cached`. Nothing changes until your instrumentation adopts v1.45.0; read its release notes when it does."
  sources={[
    { label: 'semantic-conventions v1.45.0', href: 'https://github.com/open-telemetry/semantic-conventions/releases/tag/v1.45.0' },
    { label: 'JS semconv package 1.45.0', href: 'https://github.com/open-telemetry/opentelemetry-js/releases/tag/semconv%2Fv1.45.0' },
  ]}
  deeper={[
    { label: 'Queues: messaging spans, links and attributes', href: '/blog/e2e-observability-2-queues/' },
    { label: 'Databases and Redis: what the stable db.* conventions changed', href: '/blog/e2e-observability-3-databases-and-redis/' },
  ]}>

Released 2 November. RPC spans and call-duration metrics are stable, including gRPC and Apache Dubbo,
with new histogram bucket advice (gRPC uses the 41 boundaries from gRPC's own proposal A66). RPC
headers and trailers moved to release candidate. Many Kubernetes and container metrics (uptime,
filesystem, network, paging faults, CPU usage) and the JVM file descriptor metrics are release
candidates too. Also in it: opt-in `http.request.body.content` and `http.response.body.content`
attributes (they may carry sensitive data), `service.peer.name` deprecated in favour of
`server.service.name` and `client.service.name`, and the `enduser.*` deprecation from October.

</Item>

<Item id="collector-165" title="Collector v0.165.0: zstd memory bounded, confighttp stable, SignalFx receiver removed" label="breaking" date="2026-11-07"
  why="The zstd and nesting fixes close ways a small crafted payload could make a Collector allocate a lot of memory or overflow its stack. The removals and renames break configs and queries on upgrade."
  todo="Upgrade to contrib v0.165.1 (9 November), which reverts a dependency bump in the resource detection processor. Watch the new startup warning if a pipeline uses both the batch processor and exporter batching."
  sources={[

  deeper={[{ label: 'OTTL v1, one statement at a time', href: '/blog/ottl-v1-hands-on/' }]}>

Core v0.165.0 (6 November) and contrib v0.165.0 (7 November). Security-relevant fixes: the gRPC and
HTTP servers now bound the zstd decoder window by the configured maximum message or body size, and
pdata limits nesting depth to 100 when unmarshalling attribute values. `confighttp` is marked stable,
and four of its deprecated fields are removed. The `queue_batch` processor is beta. In contrib, OTTL
gains an experimental span-link context, and the transform processor puts new functions behind a
`processor.transform.enableExperimentalFunctions` gate while they are experimental.

</Item>

3.1.0 and experimental 0.301.0 (5 November) raise the API peer floor to 1.10.0, deprecate
`envDetector` in favour of two separate detectors, and mark the `service.instance.id` detector
stable. `startNodeSdk()` now covers the environment-variable configuration path, and `new NodeSDK()`
users get `os.*` and `service.instance.id` resource attributes by default. The project's blog post
on 3.0 (5 November) adds that complex attribute values are supported on span and log attributes.

</Item>

<Item id="spec-week" title="Spec: environment-variable carriers stable, security exception widened" label="stable" date="2026-11-04"
  why="Batch jobs and CLI tools can pass trace context to child processes through `TRACEPARENT`-style variables with a stable contract. And a minor SDK release may now raise its minimum runtime when that runtime no longer gets security fixes."
  todo="Nothing to change yet; both are merged, not released (the latest spec release is v1.62.0). When you pin SDK versions on an old runtime, read minor release notes for a raised minimum."
  sources={[
    { label: 'spec PR #5389: env var carriers stable', href: 'https://github.com/open-telemetry/opentelemetry-specification/pull/5389' },
    { label: 'spec PR #5404: security exception for runtime and dependency requirements', href: 'https://github.com/open-telemetry/opentelemetry-specification/pull/5404' },

On 3 November the specification marked environment variables as context propagation carriers
stable, after the feedback period announced on the OTel blog. On 4 November it extended October's
security exception: stable SDKs and contrib components may now tighten supported runtime or
dependency versions in a minor or patch release, when that addresses a concrete security risk, and
the release notes must say so.

</Item>

The release PR merged on 30 October created GitHub tags for `browser-sdk` 0.7.0 and
`browser-instrumentation` 0.10.0. Both are breaking: a browser-native instrumentation base class,
and the SDK no longer sets a default HTTP exporter. They also add element timing instrumentation.
The npm publish job waited for approval and was rejected on 6 November. Meanwhile a
`reportSoftNavs` option for web vitals on single-page route changes was merged on 5 November and is
not on npm yet. Our part 4 of "OpenTelemetry in the browser" has the full timeline.

</Item>
